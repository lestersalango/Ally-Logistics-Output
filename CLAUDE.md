## Business context

A freight brokerage books loads: the customer pays us, we pay a carrier, and the difference is our margin. Operations wants a **carrier × lane scorecard for October 2026**: loads, revenue, cost and margin, plus whether a carrier hauled while not legally authorized. The business rules in `carrier_scorecard_exercise/data_dictionary.md` win over anything written here.

**Today:** nothing; it's a take-home-style exercise, presented live at the interview.
**Data ready by:** daily 06:00 `America/New_York` (job schedule created paused).
**Out of scope:** metric views, bundles, CI, prod. (A dashboard was added on request; see step 5.)

The pipeline must answer:
- How many Delivered loads did each carrier haul on each lane (origin state → destination state) with an October 2026 pickup date in Eastern time?
- What revenue, carrier cost, gross margin and margin % did we make on each one?
- How many of those loads did the carrier haul while unauthorized, and how many have a carrier we can't find in FMCSA?

## Source data

- **TMS loads (`loads.csv`):** a change feed in CSV with the full record on every change, unordered and with re-sends. It has 3,200 rows covering 1,800 distinct loads (1–6 versions each). It lands as files, the full file today and new change-feed rows later.
- **FMCSA census (`fmcsa_carriers.csv`):** a CSV snapshot with one row per DOT, 220 carriers (`ACTIVE` 181, `REVOKED` 23, `INACTIVE` 16). Each delivery replaces the previous one.

**Access:** CSVs land in `/Volumes/workspace/default/interview/raw/`. The volume exists and is empty (checked 2026-11-18), and Lester owns it.
**Personal data:** none (company names and DOTs only).

**Known problems to catch.** I found these by profiling locally on 2026-11-18:

| # | Trap | Handling |
|---|---|---|
| 1 | 62 exact duplicate rows; 39 loads tie on their latest `last_modified`, with identical content. | Latest version per `load_id` via `row_number()` ordered by `last_modified desc`, with a deterministic tie-breaker. |
| 2 | File order isn't time order: for 445 loads the last row in the file isn't the newest. | Never "last row wins", and never `dropDuplicates` without ordering. |
| 3 | 135 loads had `carrier_cost` corrected after delivery. | The latest version carries the corrected cost. |
| 4 | DOT typed by hand: `00983756`, ` 1234567 `, `USDOT 1234567`, blank. Without cleaning, only 1,165 of 1,366 loads match FMCSA. | Strip `USDOT`, trim, cast to `BIGINT`; blank becomes null. |
| 5 | `pickup_ts` is UTC but reporting is Eastern: UTC-October gives 1,358 loads, ET-October gives **1,366**. | `to_date(from_utc_timestamp(pickup_ts, 'America/New_York'))`. Use the zone name, not a fixed offset. |
| 6 | Unauthorized means status_date ≤ pickup date in ET. 9 loads have it equal (they count); L-735801 flips if the date is taken in UTC. | `authority_status IN ('REVOKED','INACTIVE') AND status_date <= pickup_date_et` |
| 7 | 147 loads use a carrier that is now REVOKED or INACTIVE, but the status took effect after the pickup. | Not unauthorized. |
| 8 | Legacy `margin` leaves out accessorials (554,464.64 vs 643,949.97), and 9 rows are negative. | Ignore it. Revenue = `customer_rate + coalesce(accessorial_revenue, 0)`; margin = revenue − `carrier_cost`. |
| 9 | Blank `accessorial_revenue` on 1,217 rows. | `coalesce(…, 0)`, or revenue turns null. |
| 10 | 20 loads have a DOT that isn't in FMCSA. | LEFT join, keep them, leave `legal_name` null; they count as unverified and never as unauthorized. |
| 11 | `margin_pct` | A ratio of sums after aggregation, using `try_divide`. |
| 12 | Status must come from the current version. | Deduplicate first, then filter `Delivered`. |

Checked and clean: state codes, city whitespace, timestamp format, unique FMCSA DOTs, every Delivered load has a carrier and a cost, and no load changes carrier between versions.

### 3. Medallion
- **Bronze:** both CSVs read as strings (no schema inference), plus `_source_file` and `_ingested_at` → `bronze_loads` (3,200 rows) and `bronze_fmcsa_carriers` (220 rows).
- **Silver:** `silver_fmcsa_carriers` is typed. `silver_loads` is typed, has a cleaned DOT and `pickup_date_et`, and holds one row per load (1,800). It is loaded **incrementally with `MERGE`**: take the latest version per `load_id` in the batch, update when `src.last_modified > tgt.last_modified`, and insert when there's no match. Show that a rerun changes nothing and that a later version updates the row.
- **Gold:** `gold_carrier_lane_scorecard` with exactly the columns in the problem brief, reconciled against the expected totals.
- **Data-quality checks:** `assert` cells that fail the run if any of these break:
  - one row per `load_id` in silver;
  - no non-blank DOT failed to parse;
  - no Delivered load is missing a cost or pickup time;
  - gold totals equal the silver totals for October ET Delivered loads;
  - `unauthorized + unverified ≤ load_count` on every row.
- A `force_dq_failure` widget (default `false`) breaks one check on purpose, so the failure email can be tested.
